    服务维护的关键：日志与请求链路

    我们在之前的docker和nginx章节都有简单提到如何调取log（日志），现在讲讲为什么需要它。服务程序跑起来了，并不意味着服务可维护。

    当curl返回了错误代码，只知道失败是没有意义的，我们接下来就要排查请求到底到达了服务链条的哪一层级——就像是高中生学理科的那样，真正有用的学习不是一直刷题犯错误，而是整理错题本，明晰到底是哪里出现了问题。日志便是我们确认错误犯在哪里的好工具。

    1. 日志系统

    我们往往是根据服务框架来放置日志系统。就比如，根据我们现在的框架，我们的日志大概分为三级：

    Client
  ↓
Nginx
  ↓        access.log / error.log
FastAPI
  ↓        Python logging → stdout/stderr
systemd
  ↓        journalctl -u fastapi-demo
DeepSeek API

    我们涉及了logging、systemd journal 和 journalctl 三个不同的角色。

    • logging：Python的logging包，我们在main.py自定义记录什么进日志的工具。程序通过 logger.info() / logger.exception() 输出
    • systemd journal：服务部署时，我们通过logging在terminal输出的日志 stdout/stderr 被 systemd 接走并写进 journal
    • journalctl： 只是查看 journal 的日志查询工具。

    在git章节里，我们做了开发环境和生产环境的分离，所以日志的生产也会有一定的区别。本地开发的时候，log会直接在terminal stdout输出，没有经过systemd journal；但在生产环境时，因VPS端我们已经开放了systemd服务，它会接走我们log，就如上面所述。“生产环境中，请求链路上的 Nginx 日志、应用日志与 systemd journal 才会共同发挥作用。

    2. FastAPI 应用日志设计

    理清了日志系统的层级关系后，我们要开始改造我们的main.py，为业务链路设计应用日志。每增加一个外部依赖或关键的业务步骤，就要考虑这个步骤是否留下可观测的信息。

    比如说，我们当前fastapi-demo的/chat功能接口依赖DeepSeek API，所以重点记录请求是否进入、外部 API 调用耗时、token 使用量以及异常信息。以后如果增加 RAG、数据库、Tool Calling 等模块，也应该对新的关键链路做类似的日志设计。

    import logging
import time

logging.basicConfig(level=logging.INFO)
logger = logging.getLogger(__name__)

@app.post("/chat")
def chat(request: ChatRequest):
    start_time = time.time()

    logger.info(
        "request received message_length=%d",
        len(request.message)
    )

    try:
        api_start = time.time()

        response = client.chat.completions.create(...)

        api_duration = time.time() - api_start
        total_duration = time.time() - start_time

        logger.info(
            "request completed api_duration=%.2fs total_duration=%.2fs "
            "prompt_tokens=%s completion_tokens=%s total_tokens=%s",
            api_duration,
            total_duration,
            response.usage.prompt_tokens,
            response.usage.completion_tokens,
            response.usage.total_tokens,
        )

        return {"answer": response.choices[0].message.content}

    except Exception:
        logger.exception("DeepSeek API request failed")
        raise

    在新加的代码部分，我有几个点要特别提及。

    • message_length 能知道请求规模但不泄露用户原文。不必要的个人信息不要写进日志里去。
    • api_duration 能判断瓶颈是否来自 DeepSeek
    • token数量对应成本和上下文规模。logger.exception() 会在 ERROR 信息之外留下 traceback。
    • total_duration 代表了整个/chat请求从进入应用到返回结果的总耗时，可以和 api_duration 对比，判断耗时主要来自外部模型还是本地处理。

    3. 常用命令与排查实践

    我们一般在我们的云端服务器才会用到下面的指令，因为在本地开发的时候，log会输出在terminal上。

    journalctl -u fastapi-demo
journalctl -u fastapi-demo -f #持续跟踪新产生的日志
journalctl -u fastapi-demo -n 100 # 最近100条日志
journalctl -u fastapi-demo --since "10 minutes ago" #从10分钟前开始的所有日志

sudo tail -f /var/log/nginx/access.log
sudo tail -f /var/log/nginx/error.log

    接下来我们简单讲一下，如果curl返回了一个错误代码，我们要从哪里开始排查。假设这个错误代码为500。

    1. 看Nginx access.log：请求到达了服务器了吗？
    2. 看 Nginx error.log：反向代理是否存在问题？
    3. journalctl -u fastapi-demo：是否是FastAPI本身的异常？
    4. 看应用日志：那些我们在main.py为log写的代码派上用场。请求进入了吗？API 调用花了多久？
    5. 看 traceback / 外部 API 错误：排查完500后是否跟着出现了402？timeout？还是SDK的参数错误？
      • 若是402：通常说明外部 API 已收到请求，但账户余额、额度或计费状态异常。当然其他的服务402含义，需要结合上流API的错误信息判断。
      • 若是timeout：说明请求已经发出，但在设定时间内没有正常完成，需要进一步判断是网络、上游 API 还是请求规模导致
      • 若是SDK参数错误：应该是参数接口混用或调用方式出现了问题。例如此前遇到的 choice/choices、messages 参数接口混用等。

    4. 日志生命周期与下一步

    因为磁盘有限，Nginx 文件日志不能无限增长，Linux 会轮转、压缩和删除旧日志；systemd journal 自己也有空间管理机制。现在呢，我们做的操作还是最基础的logging。后面我们才会进入更加结构化的logging，包括request ID、将日志分等级、监控指标甚至Prometheus。但那都是当服务足够复杂化时候，我们才需要的工具。

    工具不是越复杂越好，而是越适合我们项目的体量越好。
