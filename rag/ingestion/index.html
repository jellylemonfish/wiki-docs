    RAG数据摄取与离线知识库的构建：Ingestion

    在我们完成链路设计后，我们就要从知识库的搭建开始。我们在本节要完成文档切分、向量化、建立索引并对其进行存储的整个过程。

    1. 知识库范围和目录扫描

    我们第一版 RAG 的知识库范围是，只使用我们现有 wiki-docs/docs/ 里的 Markdown 文档，不额外找数据。这样做的目的是让助手能够基于项目本身已经沉淀的部署工程文档来回答问题。

    在 FastAPI 项目里新建一个专门放 RAG 代码的目录，例如 rag/。新建 rag/ingest.py，先实现“扫描并读取所有 .md 文件”。我们的伪代码思路如下四步：

    找到 docs 文件夹

documents = []

对于 docs 里面的每一个 md 文件:
    读取文件
    把 文件名 + 文件内容 放进 documents

return documents

    在定位知识库的时候，为了避免依赖运行命令是所在的工作目录，我们可以从当前的ingest.py所在的位置构造路径：

    from pathlib import Path 
DOCS_DIR = Path(__file__).parent.parent.parent / "wiki-docs" / "docs"

    这么做的好处是，无论我们从哪个目录运行 ingest.py，都能正确定位到 wiki-docs/docs 目录，避免“本地能运行，但换个入口就找不到文件”的问题。

    然后，我们将使用Path.rglob("*.md")来递归查找所有 Markdown 文件。例如，当目录中同时存在 nginx.md、docker.md 与 rag/ingestion.md 时，Path.rglob("*.md") 都会找到它们；而 file.relative_to(DOCS_DIR) 会将绝对路径转换为相对于知识库根目录的路径，例如 nginx.md 或 rag/ingestion.md。因此，知识库迁移到另一台服务器或另一份本地目录后，记录的数据仍然保留可读、稳定的来源信息。

    function `load_markdown_file()` 
    from .ingest import load_markdown_files
from langchain_text_splitters import MarkdownTextSplitter

def split_markdown_files() -> list[dict]:
    """
    Split the content of markdown files into smaller chunks.
    """
    splitter = MarkdownTextSplitter(
        chunk_size=1000,
        chunk_overlap=150,
    )

    chunks = []

    for doc in load_markdown_files():
        for chunk_id, text in enumerate(splitter.split_text(doc["content"])):
            chunks.append({
                "source": doc["source"],
                "chunk_id" : chunk_id,
                "content": text
            })

    return chunks


    除此之外，读取阶段不应只保存文本内容，还需要同时保存其来源。source是后续每一个chunk都要继承的 metadata。检索到相关内容后，它可以帮助系统说明答案来自哪篇工程文档；在调试检索效果时，也能快速判断是没有召回正确文档，还是文档被切分或向量化后失去了关键上下文。方便我们定位数据。如：

    { "source": "nginx.md", "content": "# Nginx\n..." }

    至此，原本分散在各个 Markdown 文件中的内容已经被统一读取并附上来源信息，方便后续的文档切分、向量化和索引建立。

    2. 文档切分

    向量检索的基本单位不应该是整一篇markdown文档，而是能表达相对完整语义的较小文档块，我们通称为chunk。若直接为整篇文档生成一个向量，文档同时包含多个主题时，这个向量会混合所有内容。而且，用户询问其中一个具体问题时，检索结果也难以精确定位到真正相关的段落。

    所以在embedding前，我们先要把每个文档拆分成夺格chunk，并继承原文档的来源信息。我们将写spliter.py实现这个功能。如：

    { "source": "nginx.md", "chunk_id": 3, "content": "..." }

    其中source表示该chunk来源的原始文档，chunk_id是该文档中chunk的编号，content是chunk的具体内容。

    我们第一版RAG的切分工具是使用LangChain提供的MarkdownTextSplitter:

    from .ingest import load_markdown_files
from langchain_text_splitters import MarkdownTextSplitter

def split_markdown_files() -> list[dict]:
    """
    Split the content of markdown files into smaller chunks.
    """

    splitter = MarkdownTextSplitter(
        chunk_size=1000,
        chunk_overlap=150,
    )    

    chunks = []

    for doc in load_markdown_files():
        for chunk_id, text in enumerate(splitter.split_text(doc["content"])):
            chunks.append({
                "source": doc["source"],
                "chunk_id" : chunk_id,
                "content": text
            })

    return chunks

    chunk_size=1000 表示每个 chunk 的目标最大长度约为 1000 个字符；chunk_overlap=150 表示相邻 chunk 会保留约 150 个字符的重叠区域。重叠的作用是降低文本恰好在关键句中间被截断的风险：即使某一句话跨越切分边界，前后两个 chunk 仍会共享一部分上下文。

    我们最开始的参数是 chunk_size=500, chunk_overlap=150，这个配置让单个 chunk 较短，并通过较大的 overlap 尽量保留上下文。但在实际打印并检查切分结果后，发现项目文档并不只是纯文本 Markdown，其中还包含 HTML 页面结构、CSS 样式与 JavaScript 函数。较小的 chunk 容易将一段完整的 <style>、<script> 或函数实现从中间切开，导致检索到的文本缺少必要上下文。最终，我们适当增大了chunk的大小，并降低overlap，避免重复内容过多而产生大量近似检索结果。

    当然，目前的第一版依旧是存在问题的。MarkdownTextSplitter 能利用部分 Markdown 结构辅助切分，但不会真正理解 HTML、CSS 或 JavaScript 的语法边界。例如，它无法保证一个 <script> 标签中的 sendMessage() 函数一定作为完整单元保存，也无法理解 CSS 选择器和样式规则之间的关系。 比较理想的后续方案是，针对不同的内容进行分别处理。比如按HTML标签识别组织架构、按函数和类型切分JavaScript。然而这将引入额外的解析规则设计和实现成本。 第一版RAG的主要目标是优先跑通整个链路。所以此处选了最简单的通用切分方式，我们将强化结构感知的切分方案留到后续优化。

    切分完成后，每一个 chunk都具备了文本内容、来源路径和文档内的序号。下一步我们将使用embedding模型，把这些文本块转换成可计算语义相似度的向量。

    3. 向量化

    切分完成后，每个chunk仍然还是普通文本，向量数据库没法直接理解语义的，所以我们需要embedding模型，将文本转化为固定长度的数值向量。在查询阶段，用户问题也会经过同一个 embedding 模型转换为向量；系统再计算问题向量与各个 chunk 向量之间的相似度，从知识库中找出语义最接近的内容。换言之，embedding 模型负责“检索时如何理解文本相近”，而后续的生成式 LLM 负责“如何基于检索结果组织回答”。

    RAG中生成式LLM与embedding承担的是两种不同的工作，所以我们并不要求使用同一家服务商。我们第一版RAG的聊天窗口继续使用已有的Deepseek服务，但Deepseek目前没有适合本项目直接调用的 embedding API，因此我们单独选用智谱的embedding-3完成向量化。我们需要保证在向量化阶段使用的 embedding 模型与查询阶段使用的 embedding 模型保持一致，以确保语义相似度计算的准确性。生成式LLM模型并不直接参与向量相似度的计算。我们将在embedding.py文件中实现这个功能。

    第一版RAG目的是为了尽快验证完整链路，所以先调用模型厂商的独立API。后续版本若有本地化部署或成本控制需求，只需替换 embedding 接口层，而不必重写整个 RAG 流程。

    智谱的embedding-3模型有一个可以自定义向量维度的优势。维度越高，通常能保留更多语义信息，但向量数据库的存储与相似度计算成本也会随之增加。对于我们目前当前规模较小、以中文工程文档为主的知识库，1024 维在语义表达能力与资源消耗之间提供了足够稳妥的第一版折衷方案。

    最终，我们调用的代码大致为 
    import os

from dotenv import load_dotenv
from zai import ZhipuAiClient

# from rag.splitter import split_markdown_files

load_dotenv()
client = ZhipuAiClient(api_key=os.getenv("ZHIPUAI_API_KEY"))

def embed_text(text: str) -> list:
    """
    Convert a text string into an embedding vector.
    """
    response = client.embeddings.create(
        model="embedding-3",
        input=text,
        dimensions=1024,
    )

    return response.data[0].embedding


    其中，load_dotenv() 用于加载环境变量文件 .env，确保 ZHIPUAI_API_KEY 能够被正确读取。client = ZhipuAiClient(api_key=os.getenv("ZHIPUAI_API_KEY")) 用于创建智谱AI客户端实例，后续通过该实例调用 embedding API。我们不会把密钥直接写进会放进公开仓库或者被推流到git上。

    在单文本测试确认接口能稳定反馈长度为1024的向量后，我们在批量处理已经切好的chunks。至此，我们每一条数据都同时包含原始文本、来源、文档内序号与对应向量。这样，这些数据就可以直接存入向量数据库，下一节我们将介绍如何基于这些向量建立索引。

    { "source": "nginx.md", "chunk_id": 3, "content": "...", "embedding": [0.012, -0.034, ...], }

    4. 建立索引

    在完成 ingest.py, spliter.py， embedding.py 的实现后，我们需要一个离线建库的脚本build_index.py，将它们三个功能模块串联起来。注意：它不参与用户的实时请求，它通常只有在我们更新文档、需要重建索引的时候运行。我们在service小节提到的部署脚本deploy.sh中，会根据文档变更情况决定是否调用该脚本。

    对应的实现代码 
    from .splitter import split_markdown_files
from .embedding import embed_chunks
from .vector_store import save_chunks,get_collection

def build_index():
    chunks = split_markdown_files()
    print(f"Chunks: {len(chunks)}")

    embedded_chunks = embed_chunks(chunks)
    print(f"Embedded chunks: {len(embedded_chunks)}")

    save_chunks(embedded_chunks)

    collection = get_collection()
    print(f"Collection count after save: {collection.count()}")

#%%
if __name__ == "__main__":
    build_index()


    这个脚本本身不具备具体的业务逻辑，它只是作为一个编排曾，按照固定的顺序调用功能模块模块，保证每个模块的职责清晰。在deploy.sh脚本中，我们会通过python -m rag.build_index 来调用该脚本，从而可以让python将rag识别成项目包，从而稳定分析诸如from (rag).embedding import embed_chunks的绝对（或相对）的导入路径。

    就此，离线建库的流程就完成了。在下一小节中，我们会讨论那些需要网络的流程的其他部分。
