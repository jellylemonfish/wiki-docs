    RAG服务性能评估：evaluation

    在前面的几节中，我们完成了RAG服务从无到有的搭建、并连接至FastAPI，实现了用户通过HTTP接口与RAG系统进行交互的能力。接下来，我们需要对该服务的性能进行评估，以确保其在实际使用中的响应速度和检索准确性。

    Date: 2026-09-17 16:29:06

    开发顺序：← 上一节：RAG服务接入

    1. 设计要求

    本节对系统进行第一轮人工 evaluation. RAG虽然能够跑起来，但这不代表这个服务就值得用户的信任。接口能返回一段通顺的话，只能证明我们的这条技术链通畅，但它没有证明系统找到了正确文档、没有遗漏关键上下文，也没有证明它在不知道时会停止猜测。Evaluation 就是把这些问题从主观印象变成可复现的证据。在针对我们RAG v1 版本的评估中，我们的本次目标是要验证下面这些问题：

    1. 检索是否召回正确来源
    2. 回答是否真正依据这些来源
    3. 知识库没有信息或问题前提错误时，它是否能做到明确拒绝回答
    4. 跨文档和全局性的问题的边界在哪里

    本轮测试在已部署的 /chat 接口上执行。每一次请求都会经过同一条链路，从用户问题到检索，再到生成回答，整个过程都在评估范围内。评估中，我们会将retrieval 和 answer 分开记录。（因为一个回答可能在事实层面正确，但没有检索到最直接的证据；也可能检索到局部正确的资料，却无法完成跨文档综合）。

Nginx 是什么？
根据文档，Nginx 是一个高性能 Web Server 和反向代理服务器。它的主要职责包括：

直接响应 HTTP 请求，例如返回静态网页；
将用户请求转发给后端服务，作为反向代理使用。
在生产环境中，Nginx 通常作为应用前的统一入口，负责接收公网请求，再转发给内部应用，从而避免直接暴露内部服务端口，提升安全性与管理能力。

为什么项目中使用 Tailscale Funnel，而不是 Cloudflare Tunnel？
根据现有文档，项目改用 Tailscale Funnel 而不是 Cloudflare Tunnel 的原因是：

通常可以用 Cloudflare Tunnel 来把服务暴露到公网，但 Cloudflare Tunnel 要把稳定的 hostname 建立在“用户能够控制一个 Cloudflare zone”的前提上。
当前项目的 ICP 备案还没有下来，因此不方便正式启用自己的域名，也就无法通过 Cloudflare Tunnel 做一个长期稳定的公网暴露服务。

也就是说，选择 Tailscale Funnel 主要是受当前 ICP 备案和域名条件的限制，作为 Cloudflare Tunnel 的替代方案。文档没有提到其他更详细的对比原因。

这个项目从本地 FastAPI 到公网网页，完整请求链路是什么？
根据现有文档，这个项目的请求链路可以概括为“浏览器 → 公网 IP → Nginx → Uvicorn → FastAPI → 原路返回”。具体分两种场景：

1. 生产环境完整链路
用户在浏览器访问公网地址，例如 http://公网IP/docs 或通过 HTTP/HTTPS 访问服务器。
请求中包含三个定位信息：
IP：找到哪台服务器，即云服务器公网 IP；
端口：找到服务器上的哪个程序；
路径：找到程序提供哪个功能，例如 /docs。
请求经互联网到达云服务器的公网 IP。
生产环境中，所有通过 HTTP/HTTPS 访问该服务器的请求，会首先到达 Nginx 监听的 80/443 端口。
Nginx 读取请求里的 Host，匹配对应的 server block，再执行对应的 proxy_pass，把请求转发到内部运行的 FastAPI 服务。
内部 FastAPI 服务由 Uvicorn 监听网络端口。Uvicorn 接收 Nginx 转发的请求，并交给 FastAPI 处理。
FastAPI 根据请求路由执行对应业务逻辑，生成响应。
响应再经 Uvicorn 返回给 Nginx，Nginx 最终返回给公网浏览器，用户看到网页或接口结果。
可以表示为：

浏览器 → 互联网 → 云服务器公网 IP:80/443 → Nginx → proxy_pass → Uvicorn → FastAPI → 响应返回 Nginx → 浏览器

2. 开发/直连方式
文档也提到，部署过程中可以通过公网 IP 8000 或 VS Code Remote SSH 访问服务。若直接访问，链路类似：

浏览器 → 公网 IP:8000 → Uvicorn → FastAPI → 响应返回浏览器

但需要注意：

若 Uvicorn 使用 --host 127.0.0.1 --port 8000，服务只绑定服务器自身回环接口，只能服务器内部访问，公网请求无法直接访问。
若 Uvicorn 使用 --host 0.0.0.0 --port 8000，表示监听服务器所有网络接口；如果安全组和防火墙允许，则内网或公网均可能访问。
3. 关键分工
FastAPI 本身不会监听网络端口，它负责定义接口路由、解析请求数据、执行对应业务逻辑并生成响应。
Uvicorn 是 ASGI 服务器，负责接收网络请求，并把请求交给 FastAPI 处理。
生产环境中，FastAPI 不会直接暴露在公网，而是由 Nginx 作为接收请求的入口代理。
具体域名解析、HTTPS 证书、Nginx 的 server_name/proxy_pass 目标端口、安全组和防火墙规则等细节，根据现有文档，暂时无法确定。文档也没有说明“开发者本机运行的 FastAPI 直接暴露到公网”的过程。

如果 FastAPI 服务显示 active，但网页请求失败，应该按什么顺序排查？
FastAPI 显示 Active: active (running) 只说明 systemd 认为服务进程在运行，不代表网页请求链路一定正常。根据文档，可按下面顺序排查：

先看服务状态和日志

systemctl status fastapi-demo：确认状态。
journalctl -u fastapi-demo 查看日志；可用：
journalctl -u fastapi-demo -f 实时查看
journalctl -u fastapi-demo -n 50 看最近 50 条
在服务器本机验证 FastAPI 本身是否正常
执行：curl http://127.0.0.1:8000/docs。
文档说明：如果成功，说明本机路由正常、Uvicorn 正在运行、服务加载成功；但 curl 是模拟本机访问，不代表公网访问一定成功。

如果本机 curl 成功，但网页请求失败，检查请求链路
网址访问包含三层定位：

公网 IP：是否找对服务器
端口：是否是 8000
路径：如 /docs 是否正确
文档提到，外部访问通常通过公网 IP 或 VS Code Remote SSH；而 127.0.0.1 只是设备自己访问自己。
如果涉及 Nginx / 反向代理，并且拿到 500 等错误码，按文档顺序查

Nginx access.log：请求是否到达服务器
Nginx error.log：反向代理是否存在问题
journalctl -u fastapi-demo：是否 FastAPI 本身异常
应用日志：请求是否进入、API 调用耗时等
traceback / 外部 API 错误：如 402、timeout、SDK 参数错误等
修改配置后
按文档要求：先 systemctl daemon-reload，再重启服务。

如果出现错误服务自动重启导致内存溢满等连带问题
登录云服务商对实例进行重启，再通过 VNC 远程登录修改配置，避免 SSH 多次触碰重启机制。

总结：先确认服务状态和 journalctl 日志，再用本机 curl 127.0.0.1:8000/docs 区分是 FastAPI 本身问题还是外部访问链路问题；若涉及 Nginx，再按 access.log → error.log → journalctl → 应用日志 → traceback/外部 API 错误 排查。
具体失败原因仅凭 active 无法确定，文档也未涉及安全组、防火墙等设置，需要结合实际日志进一步判断。

    基于上面的benchmark cases表和完整的对话测试，我们可以得到以下结论：

    1. 单文档事实型 query 基本可靠

    第 2 题和第 3 题表明，针对定义明确、信息集中在单一文档中的问题，v1 可以稳定检索到相关内容并生成准确回答。例如，系统能够正确说明 Nginx 的职责，也能够根据现有部署资料回答 FastAPI 监听地址与端口。第 3 题中，模型还主动区分了“文档明确写出”与“通过 Nginx 转发配置推断”的信息。这说明 prompt 中关于证据边界的约束已经发挥作用。

    1. 缺失知识与错误前提的拒答表现良好

    第 7、8、9 题验证了 v1 的 grounded answer 行为。对于 Kubernetes、agent-demo 和作者信息，系统没有将通用知识或未来规划伪装成项目事实，而是明确说明当前文档不足以确认答案。尤其是第 8 题目，说明 RAG prompt拒答策略有效的。哪怕召回了包含 “Agent” 规划的文档，系统仍能够区分“未来计划”与“已有 agent-demo 项目实现”，不编造不存在的项目细节。

    但第 9 题暴露了知识库覆盖范围不足，而不是模型行为错误。现有 corpus 没有包含作者署名，因此“暂时无法确定”是当前最可靠的回答。

    1. 闲聊会产生无意义 retrieval

    第 1 题的回答本身正常，但系统仍为“您好”检索了 docker.md、logging.md 和 nginx.md。这些结果与用户意图无关，也没有必要展示为 sources。这说明 v1 将所有请求视为知识库问题处理，尚未区分闲聊、知识查询与复杂任务。当前语料规模较小，这不会造成严重成本问题，但会降低 source attribution 的可信度。我会在下个版本改善这个问题。

    1. 跨文档综合不足

    第 5 题是本轮最重要的 regression case。问题要求描述“当前项目从本地 FastAPI 到公网网页”的完整请求链路，正确回答应综合 GitHub Pages Chat UI、Tailscale Funnel、FastAPI RAG service，以及必要时的 Nginx 入口配置。实际回答虽然正确描述了“浏览器 → Nginx → Uvicorn → FastAPI”的传统服务链路，但没有检索或整合当前项目中最关键的 GitHub Pages 与 Tailscale Funnel 层。因此，它在局部技术事实层面正确，却没有回答“这个项目”的完整架构。

    这说明了固定的 top_k=3 的普通chunk-level vector retrieval 对跨文档问题存在明显局限。或许在未来的改进中，我们应该要增强这方面的灵活程度。

    1. 全局性评价类问题不足

    目前的两个 regression cases 中， RAG v1的表现都不太好。这第二个 regression case （第 10 题）中，我们能看出系统只检索到 changelog.md 与 mkdocs.md，因此只能对更新记录、基础站点结构做有限观察，并正确拒绝对“整个文档站质量”下完整结论。……这不是文档站本身质量的问题，而是 query 的范围超过了单次局部 chunk retrieval 的表达能力。要评价整个站点，retrieval 至少应能覆盖首页、目录结构和多个具有代表性的技术章节；当前 v1 没有这类站点级或文档级视角。

    1. Source attribution 仍可能不准确

    部分回答的内容与展示来源并不完全一致。例如，第 3 题的回答使用了 Nginx 转发配置相关事实，但返回 sources 为 git.md 与 fastapi.md；第 9 题则为作者信息问题返回了无关文档。这意味着，v1 的 sources 目前表示“被检索到的文档来源”，不等于“最终回答中每一句事实的精确引用”。因此，source chip 已可用于帮助用户回到相关文档，但暂不应被理解为严格的 sentence-level citation。在下个版本中，应该要做这方面的强化。

    3. RAG v1 总结

    第一轮 evaluation，我们能粗略地得到以下结论：

    • single-document factual retrieval：基本可靠
    • missing knowledge / false premise abstention：表现良好
    • casual conversation：会触发无意义 retrieval
    • cross-document synthesis：不足
    • global document understanding：不足
    • source attribution：仍可能包含弱相关或不准确来源
    • corpus coverage：当前不包含作者信息，也未覆盖 PDF、代码等其他资料类型

    因此，RAG v1 已达到【面向工程文档的最小可用问答服务】目标：能够回答多数局部文档问题，也能在证据不足时拒答。但它尚不适合处理站点级总结、复杂跨文档架构说明或需要精确来源追踪的问题。

    故此，我们会对这次 evaluation 的部分 benchmark 问题进行保留，在下一轮 RAG v2 的evaluation 中继续使用这些问题进行测试和改进：尤其是 跨文档综合、全局性评价类问题以及 source attribution 的相关测试。当然，这次测试的还是有相当多的不足的。即benchmark 的问题设计还是较少，缺少组次覆盖和多样性（比如准备30个问题，3组10问），未来需要在问题设计上进一步丰富。

    以下方向是基于本轮 evaluation 得出可能改进，或许在将来的迭代会解决这些问题。

    • Query routing：将闲聊、简单问候与知识库查询区分开，避免无意义 retrieval；
    • Similarity threshold：当检索结果相关性过低时，不强行注入 context 或展示 sources；
    • Metadata filtering：利用文档类型、主题或目录层级限制检索范围；
    • Document summary：为每篇文档建立简短摘要，辅助回答跨 chunk、跨段落的问题；
    • Hierarchical retrieval：先检索相关文档，再在文档内部检索具体 chunk，以改善全局与跨文档问题；
    • Corpus expansion：在明确边界和权限后，逐步纳入 README、代码、PDF 或其他项目资料，并为作者等站点级信息提供明确来源；
    • Citation refinement：将当前文档级 source attribution 进一步改进为更接近回答事实的引用关系。
