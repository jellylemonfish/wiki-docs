    将知识库检索链路接入 Fast API：RAG service

    在上一节，我们完成了从用户问题到相关文档 chunk 的检索。接下来，我们将这一检索链路接入 Fast API，通过改装在logging篇的示例代码，实现将 RAG 服务连到之前写好的/chat的接口。

    因为时间原因，在v1版本的知识库里暂不增加对检索结果的日志记录，但在后续的改进中，可能会增加这些，包括检索耗时、命中文档数量以及相关的异常信息。

    Date: 2026-09-17 12:59:12

    开发顺序：← 上一节：RAG存储检索 ｜ 下一节：RAG评估 →

    1. 将RAG 流程封装

    我们将之前在retrieval篇中实现的知识库检索逻辑封装成一个python 函数，便于在 Fast API 的接口中调用复用同个链路。这样可以保持接口的简洁，同时也方便后续对检索逻辑进行改进。这个便是 RAG 流程内部的编排层 service.py。在建库环节，我们也有类似的编排层 build_index.py。

    from .retriever import retrieve
from .prompt import build_rag_prompt
from .llm import call_deepseek

def extract_source(chunks:list[dict])->list[str]:
    """
    extract an unique list of sources from the retrieved chunks
    """
    return list(dict.fromkeys(chunk["source"] for chunk in chunks))

def rag_answer(query:str)->dict:
    """
    retrieve relevant chunks for the given query and build a RAG prompt using them.
    """
    chunks = retrieve(query)
    sources = extract_source(chunks)
    prompt = build_rag_prompt(query, chunks)

    answer = call_deepseek(prompt)

    return {
        "answer": answer,
        "sources": sources,
    }

    在这里特别需要注意的是，这里返回的不只是 answer，还包括 sources。同一篇文档可能被拆成多个 chunk，因此先按保留顺序去重，再将来源返回给调用方。这样前端可以展示 source chip，并跳转到对应的 Markdown 文档；后续也可以将来源用于人工核验、evaluation 或回答质量排查。

    2. 改写 llm 调用

    我们在之前的篇章聊过如何接入LLM，在这里我们把曾经写在fastapi-demo项目的 main.py 中的调用逻辑单独拿出来，重新写成rag/llm.py模块，方便同时被rag项目和fastapi-demo项目复用。为了叙事统一，这部分独立的代码我们写在了 llm api章节中。

    不过我们在这里特别提一下其中的一些和 rag 项目本身有关的设计。我们在上面的service.py部分，我们只调用了 call_deepseek 这个接口，而没有关心具体的实现细节。如果将来我们更换了 LLM 提供商，只需要修改 rag/llm.py 模块，而不需要改动 service.py 中的业务逻辑。HTTP请求、鉴权和响应只保留在llm.py模块中。

    因为我们把 LLM 调用封装在 rag/llm.py 这里了，为了保证 fastapi-demo 服务本身的运作，我们需要做两件事情：

    1. 把 rag/ 组织成 python package。这样，处于 rag 项目外部的 fastapi-demo 项目也可以去复用 rag/ 下的 python 函数。
    2. 改写 fastapi-demo 的 main.py ，使其正确调用 rag/llm.py。

    3. python package

    在先前的编排过程，我们注意到在每一个 *.py 文件开头，我们能自由的去引用同个目录下的其他python脚本里面的函数。我们一般说这是相对导入，而*.py 文件被称之为模块，module。

    python package则是比 module 更高一级别的抽象对象。我们希望这样的导入写作不仅发生在同个项目目录内部，还能让这种导入方式在项目外部也能正常工作，这就是我们需要把 rag/ 组织成一个标准的 python package的原因。

    做法也很简单，直接在 rag/ 目录下添加一个空的 __init__.py 文件。这有助于python 来识别到这是一个package（本质上，这是一个防止与预加载的其他package冲突的标记）。在以后做更加复杂的项目的时候，我们可以在 __init__.py 内写入依赖的其他python 模块。但现在rag项目相对简单，我们保持空的即可。

    在之后，我们需要对 rag 项目内部的其他模块都统一改成相对导入的方式，例如：

    # before
from retriever import retrieve

# after
from .retriever import retrieve

    因此测试和启动统一从项目根目录执行（python -m rag.service），而不是直接执行某个文件(python rag/service.py)。我们用这样的方式，避免了“直接运行脚本时能 import、作为 package 使用时反而失败”的路径问题，也使模块关系更清晰。例如，我们可以在 service.py 保留一个最小的命令行测试（如下），然后在terminal 直接根目录执行 servie.py 文件。

    if __name__ == "__main__":
    query = "GitHub Actions 在这个项目里做了什么？"
    print(rag_answer(query))

    我们会在terminal看到对应的执行结果。现在，我们可以在fastapi-demo 项目通过 from rag.llm import call_deepseek 的方式去引用 rag/llm.py 中的函数了。

    4. 接入 FASTAPI /chat

    我们的目的是，在fastapi-demo 接入 rag 时，尽可能地保留原本的请求和响应形状的稳定。前端继续发送的格式不变。服务端，则在原有的answer字段之外怎加 source。

    现在版本的fastapi-demo 的主程序 main.py，但除了调用了rag之外没有其他变化 
    
import time
from datetime import datetime
import logging # 引入日志


from fastapi import FastAPI
from pydantic import BaseModel
from fastapi.middleware.cors import CORSMiddleware
from rag.service import rag_answer #加入了我们写好的rag包内容

logging.basicConfig(level=logging.INFO)
logger = logging.getLogger(__name__)

app = FastAPI()
app.add_middleware(
    CORSMiddleware,
    allow_origins=["https://yourGithub.github.io"],  
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)


class ChatRequest(BaseModel):
    message:str

@app.get("/")
def read_root():
    return{"message": "AI service is running!🎉"}

@app.post("/chat")
def chat(request: ChatRequest):
    if not request.message.strip():
        return {"answer": "Message cannot be empty.", "sources": []}
    # log the info of message
    start_time = time.time()
    request_time = datetime.now().strftime("%Y-%m-%d %H:%M:%S")
    # we donot need to record user original message 
    logger.info(f"request received length={len(request.message)}")

    try:
        result = rag_answer(request.message) # 调用 rag 服务获取回答和来源
        latency = time.time() - start_time
        logger.info(
            f"request_time={request_time}, total_duration={latency:.2f}s"
        )
        return result

    # catch any exception
    except Exception:
        latency = time.time() - start_time
        logger.exception(
            f"RAG request failed. request_time={request_time}, total_duration={latency:.2f}s"
        )
        raise

@app.get("/health")
def health_check():
    return{"status": "OK"}

    需要提及的几个要点：

    • 日志记录请求长度而非用户原文，避免将用户输入直接写入服务器日志
    • 正常请求记录总耗时
    • 失败请求通过 logger.exception() 保留完整 traceback。当前 latency 是端到端耗时，包含 query embedding、Chroma 检索、构建 prompt 和外部 LLM API 调用。

    前端收到响应后，将展示answer， 并将 source 渲染称可以跳转的 source chip。Chat UI 的具体演变和前端实现记录在 chat-ui部分中，本节就不重复展开了。

    5. 部署自动化

    在实际生产环境中，我们希望能有一个自动动作，将代码更新、依赖同步、索引重建与服务重启串联到一起，这就是我们放在ai-infra根目录下deploy.sh 的功能。其流程伪代码大致如下

    git pull → install dependencies → rebuild RAG index
→ restart FastAPI service → check status
    完整代码 
    #!/bin/bash

set -e

REPO_DIR="$(cd "$(dirname "$0")" && pwd)"
PROJECT_DIR="$REPO_DIR/fastapi-demo"
VENV_DIR="$PROJECT_DIR/.venv"

echo "== Check doumentation changes =="
cd "$REPO_DIR"
git fetch origin main

if git diff --quiet HEAD origin/main -- wiki-docs/docs; then
    DOCS_CHANGED=false
else
    DOCS_CHANGED=true
fi

echo "== Pull last changes =="
git pull origin main

echo "== Install dependencies =="
cd "$PROJECT_DIR"
"$VENV_DIR/bin/python" -m pip install -r requirements.txt

if [ "$DOCS_CHANGED" = true ]; then

    echo "== Rebuild RAG index =="
    "$VENV_DIR/bin/python" -m rag.build_index
else
    echo "== Documentation not changed, skip rebuilding RAG index =="
fi

echo "== Restart FastAPI service =="
sudo systemctl restart fastapi-demo

echo "== Check service status =="
sudo systemctl status fastapi-demo --no-pager

echo "== Deploy finished =="

    在这里，我想提及到做了一个“检索wiki-docs项目是否存在新文件”的动作，来减少不必要的索引重建操作。只有当文档发生变化时，才会触发 RAG 索引的重建。

    在执行deploy.sh脚本前，需要为脚本添加可执行的权限

    chmod +x deploy.sh

    之后，在VPS的仓库根目录的时候，我们就可以用./deploy.sh来执行脚本。依赖文件不直接使用 pip freeze > requirements.txt 来生成。这是因为会记录虚拟环境中的全部间接依赖，容易引入与项目无关的包；本项目改为维护最小、显式的运行时依赖列表。所以现在的阶段习惯显写那些强相关的依赖包。

    6. VPS的端到端测试

    部署后不能只看到 systemctl 显示运行中就认为 RAG 已经可用。至少需要依次验证服务状态、本地 HTTP 接口和运行日志：

    1. 检查服务状态：
    sudo systemctl status fastapi-demo --no-pager
    1. 测试本地 HTTP 接口：
    curl -X POST http://127.0.0.1:8000/chat \
  -H "Content-Type: application/json" \
  -d '{"message":"什么是 Nginx？"}'
    1. 查看运行日志：
    journalctl -u fastapi-demo.service -n 25 --no-pager

    在26年9月10日的测试中，我们的/chat 请求已经成功进入FAST API， 执行 RAG检索并到达 外部LLM调用阶段。但日志出现

    openai.APIConnectionError: Connection error.

    这说明问题不在前端、FastAPI 路由或 Chroma 检索，而位于服务进程到模型 API 的最后一段连接。排查顺序如下：

    1. 使用 curl -I 检查 VPS 能否访问模型服务商域名，先确认 DNS、网络和 TLS 层是否正常；
    2. 使用 grep 检查当前代码中实际传入 OpenAI client 的 base_url；
    3. 检查 .env 中的 API 地址和密钥是否已经更新；
    4. 确认 systemd 服务启动时能够读取正确环境变量，并在更新 .env 后重新部署、重启服务。

    最终，我们定位到 .env 文件没有正确更新，导致运行中的 FastAPI 服务没有获得正确的模型配置。更新配置并重新运行部署脚本后，接口恢复正常。
