    知识库问答系统：RAG

    在完成 FastAPI 服务接口与 Wiki 工程文档站点的基础上，本阶段进一步将两者连接起来：以 Wiki 文档作为知识库，并在原有聊天接口上加入检索增强生成能力。由此，前期完成的 Web Service、部署链路与工程文档开始组成一个完整的 AI 问答系统——一个轻量级 RAG（Retrieval-Augmented Generation）问答系统。

    目前的版本（v1.0）涵盖了从文档处理、索引构建到问答服务的全链路。它能： - 能够读取指定的wiki markdown文档，并建立持久化的向量索引。 - 用户通过网页聊天界面提问时，系统会先retrieval，再仅基于检索到的工程文档上下文生成回答 - 文档信息不足的时候，通过prompt约束模型明确说出无法确定 - 能够返回文档来源并进行最基础的citation展示 - 能够通过公网HTTPS链路，从Github pages前端访问部署在服务器上的RAG API

    1. RAG项目框架

    RAG项目的链路分为两个阶段： 1. 文档处理与索引构建阶段：并不需要网络的离线阶段。包括文档切分、向量化、向量存储等模块，负责将工程文档转化为可检索的Chroma向量索引。在目前的版本中，每一次更新文档都需要重新构建索引。 2. 问答与服务阶段：依赖网络的在线阶段。包括检索、提示模板、大模型接口、服务接口等模块，负责基于用户问题进行检索、生成回答并最终通过FastAPI和前端窗口对外展示。

    当前第一个版本的完整链路为：

    Markdown → chunks → embeddings → Chroma → retrieval → context → LLM → FastAPI → Tailscale Funnel → GitHub Pages Chat UI

    下面是更细致的模块说明： - ingest.py：读取 Wiki 中的 Markdown 文档，并统一整理文档来源与正文内容。 - splitter.py：将完整文档切分为适合 Embedding 与 retrieval 的文本块。 - embedding.py：封装 Embedding 模型调用，将文本转换为向量。 - vector_store.py：管理 Chroma 向量数据库及 collection。 - build_index.py：串联文档读取、切分、Embedding 和写入向量库，完成离线索引构建。 - retriever.py：根据用户 query 在向量数据库中检索相关文本块。 - prompt.py：将检索到的 context 与用户问题组织为最终 Prompt。 - llm.py：封装 LLM API 调用。 - service.py：组织完整 RAG pipeline，对上层应用暴露统一问答接口。

    （上面这两个是不是重复了）

    2. 项目限制

    经过evalution测试，当前版本的 RAG 系统存在以下限制： - 当前的chunk定义比较固定，主要是针对自然语言的markdown，对代码块和表格的处理不足 - 所有query都会默认地进入retrieval，尚未加入闲聊与知识库问题的路由 - 跨文档综合能力高度依赖top-k retrieval策略，对于有关于全局的query表现有限 - 对于多轮对话的上下文管理尚未完善，可能导致回答不够连贯 - citation precision仍然有进一步提升的空间，偶尔会有出现无关的引用

    在下一个版本会尽可能地解决这些问题。
