    从markdown到网站：mkdocs

    在工程实践中，代码并不是项目的全部。随着功能不断增加，我们还需要持续记录配置、问题排查方法和设计思路。如果这些内容知识零散地存在于聊天记录、笔记或者代码注释诸如此类的地方，后续的查找和维护都会变得相当的困难。因此，我们通常会使用 Markdown 去编写结构化的工程文档：语法简单、也便于版本控制！同时，我们可以通过mkdocs将我们的markdown文档集合变成一个带有导航和搜索工具的静态网站。这样，我们既保留了 Markdown 易于编写和维护的优点，又能够以网站的形式统一展示整个项目文档，极大降低前端页面本身的维护成本。

    我们的wiki-docs项目便由mkdocs构建。

    1. 安装

    首先，我们先新建一个目录，作为我们的wiki-docs的主要位置。

    cd ~
mkdir wiki-docs #建目录
cd wiki-docs
python3-m venv .venv #构建虚拟环境
source .venv/bin/activate #进入虚拟环境
pip install mkdocs #安装mkdocs
mkdocs new . #自动生成项目结构

    生成完成后，我们的结构将如下

    wiki-docs/
├── docs/ # 放置所有md文件的地方
│   └── index.md
└── mkdocs.yml # 网站索引导航

    平日，我们将主要写docs/*.md 和维护我们的网站导航 mkdocs.yml。除此之外，如果带有图片内容，我们也可以新建一个 docs/pics放置我们的图片文件。

    接下来我们将花费大量的时间在写.md工程文档，作为我们wiki-docs的内容主体。这里推荐一个很好的国人markdown教程，以及其方便的语法速查表。通过学习markdown，我们可以快速的构造笔记、演示文稿、网站甚至电子书。不过我们并不在此处累述markdown的优势与劣势。

    2. 于服务器上部署

    完成了一定的.md工程文档之后，我们便可以通过mkdocs渲染静态网站，并部署在我们的服务器上了。首先先安装我们的网站主题，这次我们选择了流行的material 主题风格。至于其他的readthedocs 和第三方主题，请详见mkdocs的官方文档。

    pip install mkdocs-material # 安装material主题

    安装完成后，我们便修改mkdocs.yml配置以满足我们的需求。nav部分是我们的网站导航，根据到目前为止，mkdocs.yml的主体内容大致如下：

    site_name: Shien's AI Infrastructure wiki

theme:
  name: material
  highlightjs: true

nav:
  - Home: index.md
  - Infrastructure:
      - Linux基础: linux.md
      - 网络基础: network.md
      - 反向代理: nginx.md
      - 容器化部署: docker.md
      - API服务化: fastapi.md
      - 日志监控: logging.md

  - AI Systems:
      - LLM API接入: llm-api.md

  - Engineering:
      - git工作流: git.md
      - 网站部署: mkdocs.md

    接下来我们便可以生成静态网站，并托管给nginx。

    mkdocs serve -a 127.0.0.1:8080 #本地预览
mkdocs build
sudo cp -r site/* /var/www/wiki-docs/ #把 MkDocs 构建出来的网站文件复制到 Nginx 对外提供服务的目录

    以后更新了.md文件后，都是重复以下操作更新网站。

    mkdocs build
sudo rsync -av --delete site/ /var/www/wiki-docs/

    --delete 的意义是：如果我们从网站里删掉了某个页面，它也会从部署目录删除旧文件，避免残留。同时，我们也需要修改nginx配置，以便于我们的网站能顺利的在服务器部署。首先确认目录 sudo ls /etc/nginx/sites-enabled/，修改default文件：

    server {
    listen 80 default_server;
    listen [::]:80 default_server;

    server_name _;

    root /var/www/wiki-docs;
    index index.html;

    location / {
        try_files $uri $uri/ =404;
    }

    location /api/ {
        proxy_pass http://127.0.0.1:8000; #把API移动到了下属/api页面
    }
}
    • 一开始这段内容是写进一个新配置wiki-docs里的。但新建 wiki-docs 配置后，同时保留了原来的 default，两者可能同时监听相同地址/端口并存在默认 server 或规则重叠。故此，后来又删除了 sites-available/wiki-docs，但 sites-enabled/wiki-docs 的软链接仍存在，于是 nginx -t 报找不到目标文件。实际上，在sites-enabled文件夹内的都是软连接，删掉坏掉的连接对程序主体并不会产生影响。
    shien@infra01:/etc/nginx/sites-available$ sudo nginx -t
nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
nginx: configuration file /etc/nginx/nginx.conf test is successful
shien@infra01:/etc/nginx/sites-available$ sudo systemctl reload nginx

    若sudo nginx -t成功，会出现以上回复。这时候，我们便可以重启nginx服务，见到我们网站的全新摸样。

    3. 于github上部署

    当然，最理想的肯定是在自己的服务器上部署。但当ICP备案还没有下来，但又因为一些原因我们急需上线我们的工程文档网站，我们可以考虑挂靠在github上。我们在git章节中，我们已经存有一个名为ai-infra的私人仓库，用来管理同步我们所有的项目。现在，我们需要写一个Github Action自动部署动作，将我们的wiki-docs部分的内容同步到一个专门用来做公开网站的新仓库上。为了方便我们后续的工作，这个新仓库的名字可以取名为wiki-docs 。

    什么是Github Action： GitHub Actions是GitHub提供的一套自动化工作流（Workflow）系统，本质上，它便是Github内置的CI/CD自动化平台。我们可以通过YAML文件描述一组“在什么条件下触发、在哪个环境中运行、依次执行哪些操作”的规则。例如，当代码被push到指定分支后，GitHub Actions可以自动拉取代码、安装依赖、执行测试、构建项目，甚至继续将构建产物部署到服务器或其他仓库中。

    在 GitHub Actions中，一个完整的自动化流程通常被称为workflow。一个workflow可以包含一个或多个job，而每个job又由多个依次执行的step组成。GitHub会为job提供一个 runner，也就是实际执行这些命令的运行环境。比如，在我们的deploy-wiki.yml中，ubuntu-22.04就表示这个部署任务会运行在 GitHub 提供的 Ubuntu Runner上。

    现在再回到我们这次部署动作的需求上。我们的需求本质是：

    1. 在每次提交到ai-infra私人仓库的commit中，如果变化涉及到wiki-docs/**，其中的wiki-docs文件夹内的内容和更改会往另一个公开仓库wiki-docspush
    2. wiki-docs公开仓库pull到更新内容后，再执行mkdocs build指令，将所有.md文件和mkdocs.yml渲染成html静态网站
    3. 渲染完成后，再push到wiki-docs仓库的main分支，通过github page功能，将网站挂靠在github.com下

    所以，通过拆解整个工作流，我们能够意识到我们需要一个跨仓库的权限凭证，让位于ai-infra仓库的github action workflow有对wiki-docs仓库的读写能力。所以，我们的第一步是生成这个凭证，在Github语境中，这个凭证名为Personal Access Token。

    1. 生成token：Github account setting > Setting > Developer setting > Personal access tokens > Fine-grained tokens > gengerate new token。名字我们可以简单取成WIKI-DOCS-DEPLOY。在Repository access部分中，我们选择onley select repositories，选择我们的wiki-docs仓库。在Repository permissions中，把contents 设置成Read and write。复制生成的token密钥。
    2. 授权：回到ai-infra仓库。Repository setting > secrets and variables > actions > new repository secret。我们把名字取成WIKI-DEPLOY-TOKEN，将刚刚复制的token 密钥粘贴进value框中。

    这样，我们就能达到让运行在ai-infra仓库中的workflow持有一个能够读写wiki-docs仓库的凭证。在等会的workflow文件里，我们就会用 ${{ secrets.WIKI_DEPLOY_TOKEN }} 代指我们的key，我们的key value不会出现在版本历史或者其他文件中。

    接下来，我们就开始写github action workflow文档。我们直接在网页端上写它。继续呆在ai-infra仓库这里——进入 Action > set up a workflow yourself。此时，GitHub 会自动创建 .github/workflows/目录和一个 YAML 文件。我们把文件名改成deploy-wiki.yml，内容大致如下：

    name: Deploy Wiki

on:
  push:
    branches:
      - main
    paths:
      - "wiki-docs/**"
      - ".github/workflows/deploy-wiki.yml"

  workflow_dispatch:

jobs:
  deploy:
    runs-on: ubuntu-22.04

    steps:
      - name: Checkout source repository
        uses: actions/checkout@v4

      - name: Setup python
        uses: actions/setup-python@v5

      - name: Install dependencies
        run: pip install mkdocs-material

      - name: Build mkdocs
        working-directory: wiki-docs
        run: mkdocs build

      - name: Checkout public repository
        uses: actions/checkout@v4
        with:
          repository: jellylemonfish/wiki-docs #这里改成你的github名/wiki-docs
          token: ${{ secrets.WIKI_DEPLOY_TOKEN }}
          path: public-site

      - name: Sync site files
        run: |
          rsync -av --delete \
            --exclude=".git" \
            wiki-docs/site/ public-site/
      - name: Push website
        working-directory: public-site
        run: |
          git config user.name "github-actions[bot]"
          git config user.email "41898282+github-actions[bot]@users.noreply.github.com"
          git add .
          if git diff --cached --quiet; then
            echo "No website changes."
          else
            git commit -m "Deploy wiki from ai-infra"
            git push
          fi
    • 【actions/checkout@v4 和 actions/setup-python@v5 】这些是官方已经封装好的自动化动作，我们通过uses:来调用。actions/checkout@v4指的是：使用名为checkout的action的 第四个主版本。actions/setup-python@v5也是同理。不过，Action也会随着Github的维护持续升级，新项目应该参考官方文档选择当前稳定版本。
    • 【41898282+github-actions[bot]@users.noreply.github.com】这个是GitHub Actions官方bot常用的noreply邮箱，用来给自动提交设置commit author。
    • 【为什么每一次commit都要配一次pip install mkdocs-material】Github Actions的每一次workflow都会从一台全新的runner开始，它本身就是一个临时环境。在任务结束之后，虚拟机都会被丢弃；所以我们在action文档里都要安装一次依赖。当然，我们其实可以通过pip cache和构造wiki-docs/requirement.txt组合配置python package 缓存。除此之外，Github也的确除了action runner之外还提供了action cache的工具，如何配置详见官方文档。但目前我们依赖并不算重，我就没有把设置做的这么麻烦。

    实际上，我们这一次实践的就是一个很具体的CI/CD workflow，不过相当的轻量。在本章节的第二小节我们之前是手动mkdocs build、复制文件和手动部署。现在，我们都把这些写进了workflow，让runner自动执行，我们就不用多次亲自执行这些指令。保存并commit了我们的deploy-wiki.yml后，我们的github action workflow便设置好了！
