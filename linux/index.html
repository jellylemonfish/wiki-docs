    打下我们在终端的第一行代码：Linux

    如果想要自训练一个vLLM模型、甚至梦想参与前沿的模型开发工作，那掌握好基础的Linux知识是迈向目标的第一步。养鱼总需要鱼缸，Linux是便是相当多工程项目的鱼缸热门且可靠的品牌。所以，他自然而然便是现代 AI infrastructure的基础运行环境最优选择之一。在AI服务的部署中，Linux 负责提供计算环境、进程管理、权限控制以及服务生命周期管理。

    本文记录在云服务器部署服务过程中涉及的 Linux 基础知识，并涉及部分实践过程和个人兴趣产生的深入学习笔记。

    Date 2026-08-28 22:56:04

    1. Linux Server Enviroment

    在实际部署 AI 服务时，通常不会直接运行在个人电脑，而是在远程 Linux 服务器上。是的，在热情澎湃地打下第一行代码之前，我们首先得租用一台远程服务器，也就是云服务厂商提供的计算实例（Compute Instance）。在这一方面，国内外自然而然有相当多的云服务器厂商。其中，国际包括：AWS（Amazon Web Services）、Google Cloud Platform（GCP）、Microsoft Azure、DigitalOcean、Vultr、Linode（Akamai Cloud）等；国内则包括阿里云、腾讯云、华为云、火山引擎、百度智能云等。不同厂商在价格、地域、网络质量、GPU 资源、控制台体验以及备案要求等方面各有差异。不过对于刚开始学习 AI 服务部署的人来说，并不需要过早纠结厂商选择：只要能够提供一台公网可访问的 Linux 计算实例，就足以完成后续绝大多数基础工程实践。 如果是需求国际节点，我用过Google Cloud和AWS，因为他们对在校师生的优惠力度更大一些；如果需求国内节点，我用过阿里云与腾讯云，在后面工程逐渐复杂化的情况下，他们能在更经济的情境下提供更多的配置方案。仅是主观体验，并不代表个人推荐倾向。

    本项目主要使用阿里云的实例综合配置，前期通过 SSH 远程连接服务器远程开发并进行运行测试。后来转移到本地开发，用git协同代码至远程服务器。

    主要环境为：

    • OS: Ubuntu Linux 22.04
    • Remote access: SSH
    • Development tool: VS code remote SSH

    2. 第一行代码：登录服务器

    云服务器创建完成之后，我们终于可以真正进入 Linux 环境。

    云服务器通常不会像个人电脑一样直接连接显示器和键盘，而是通过网络进行远程操作。最常见的方式就是使用 SSH 登录服务器。Secure shell(SSH)是一种用于远程登录服务器的协议。其他类型的协议可以在network章节检索。通过SSH，我们可以让云服务器远程执行我们的命令、管理服务器的文件和部署应用程序。 云服务商创建实例后，一般会提供服务器的公网 IP 地址。最基础的连接方式是直接打开电脑的终端，输入以下内容：

    ssh username@server_ip
# 如，ssh root@123.123.123.123， server_ip是创建完云服务器得到的对应服务器ip地址

    第一次连接服务器时，终端可能会询问是否信任该服务器的 host key：

    Are you sure you want to continue connecting (yes/no/[fingerprint])?
# 确认服务器地址无误后输入：
yes

    我们便正式的进入了远程Linux Server。现在，我们可以先不急着部署任何应用。第一件事是确认：我是谁，我在哪里，我正在操作哪一台机器，这台机器有什么资源。常见的环境检查命令有：

    whoami              # 当前用户，如我们现在的root，root用户往往拥有最高权限
pwd                 # 当前目录，首次登录时通常会位于用户的 Home Directory
hostname            # 当前主机名。在同时维护多台服务器的时候，它是相当实用的检查命令
cat /etc/os-release # 用于查看 Linux 发行版及版本信息，例如 Ubuntu 22.04。
uname -a            # 内核和架构
free -h             # 内存
df -h               # 磁盘
ls                  # 查看当前目录下的文件和文件夹
ls -la              # 更完整的目录信息，包括隐藏文件
cd /home            # 切换目录
cd ~                # 回home directory

    我们还需要准备登录用户名，以及密码或 SSH Key。我推荐我们大部分时候使用普通用户运行服务。root有完整权限，但并不建议日常运行使用。避免长期使用root用户，降低误操作的风险。

    adduser shien       # 创建名为shien的普通用户，当然，这里可以是你的名字
usermod -aG sudo shien # 把shien加入sudo用户组，使其能够在需要的时候执行管理员命令
groups shien        # 确认shien所属的用户组

    我们后续会逐步转到本地开发。在本地开发环境中，可以配置SSH key的认证减少频繁输入密码的繁琐。数字key有很多种类型，如SSH中经常配置的rsa key，也有如配置github的ed25519 key。现在，我们回到我们本地电脑的termial终端：

    ssh-keygen -t rsa -b 4096 -C "your_email@example.com" 
# rsa类型的key，4096 bit C后面跟的是注释，不一定要填邮箱
Enter file in which to save the key: #Enter
#出现了这段文字后，直接按Enter会保存到默认位置 ~/.ssh。
# 然后，我们就得到了两把钥匙，id_rsa & id_rsapub

    其中，id_rsa 是是私钥，只应保存在自己的本地电脑中，不应上传、发送给他人或提交到git仓库。id_rsa.pub是公钥，可以安全地配置到需要登录的远程服务器那里。

    ssh-copy-id shien@server_ip

    将本地公钥复制到远程服务器。它通常会把公钥追加到服务器端目标用户的~/.ssh/authorized_keys，之后再次登录SSH Server就会自动用公钥验证私钥，不再需要用户再次输入密码。

    3. Process 与 Service Management

    到这里，我们已经可以通过 SSH 登录服务器并执行 Linux 命令。接下来会遇到一个非常实际的问题：我们的应用应该怎样长期运行？

    Linux 中，一个正在运行的程序实例通常表现为一个 Process（进程）。例如，我们接下来会开发的FastAPI-demo 小项目，它的程序脚本main.py里的 FastAPI 应用需要由 Uvicorn 这个 ASGI Server 启动并对外提供服务。即直接运行uvicorn main:app --host 0.0.0.0 --port 8000 。（而关于这个main.py应该怎么写，请转入fastapi章节，我们等会就要用到）不过现在，我们可以来观察一下uvicorn:

    ps aux | grep uvicorn

    但uvicorn是有临时性的，SSH退出之后，它启动的对应服务就会停止；服务器重启之后也不会自动启动。所以，一个长期运行的服务器程序通常需要额外的 Service Manager 来负责管理。在这里，我们将请出大名鼎鼎的systemd。在现代 Linux 发行版中，systemd 是最常见的 Service Manager 和 init system。它负责启动与停止服务，自动重启与开机启动，和日志的管理。在systemd的帮助下，我们的服务链条变成了下面的模样：

    User ->systemd -> Application Process -> uvicorn -> FastAPI application (main:app)

    也就是说，Uvicorn 负责运行应用，systemd 负责管理 Uvicorn。

    假设现在我们已经完成好了fastapi-demo项目的初始化了，我们有对应的目录、主文件和其运行时的虚拟环境。为了告诉 systemd 如何启动我们的程序，我们需要创建一个.service 配置文件。首先，先打开编辑器：

    sudo nano /etc/systemd/system/fastapi-demo.service

    在里面写入：

    [Unit]
Description=FastAPI Demo Service
After=network.target 
#告诉 systemd，等网络准备好以后再启动这个服务。因为 FastAPI 要监听端口，没有网络当然没法工作。


[Service]
User=shien #指定非root用户
WorkingDirectory=/home/shien/fastapi-demo
ExecStart=/home/shien/fastapi-demo/.venv/bin/uvicorn main:app --host 0.0.0.0 --port 8000 
# ExecStart：把进入虚拟环境的命令自行合并了。
##  source .venv/bin/activate
##  unvicorn main:app --host 0.0.0.0 --port 8000
# 不过，因为 .venv/bin/uvicorn 本身就是虚拟环境里的 Uvicorn，所以直接调用它，就相当于已经进入了虚拟环境，不再需要 source activate。
Restart=always #设置自动重启


[Install]
WantedBy=multi-user.target
# WantedBy：这一行告诉 systemd，当系统进入正常运行模式时，希望这个服务也自动启动。

    完成并保存 .service 文件之后，我们还需要：

    sudo systemctl daemon-reload # 重新读取配置
sudo systemctl start fastapi-demo # 启动服务
sudo systemctl status fastapi-demo # 检查运行状态

    如果服务正常，那么就能看到Active: active (running)这一行字。现在，我们原本需要手动执行的 uvicorn main:app --host 127.0.0.1 --port 8000 变成了由 systemd自动执行和管理的。

    4. 排查流程

    实际服务器服务异常的问题，要先检查状态(systemctl status)，再查看日志(journalctl -u)确认问题。修改完配置之后，再重新加载配置(systemctl daemon-reload)并重启。日志查看的常见命令如下：

    journalctl -u fastapi-demo #查看日志
journalctl -u fastapi-demo -f #实时查看，建议配合新开一个terminal配合使用
journalctl -u fastapi-demo -n 50 #最近50条日志，适合用来追溯+缩小范围

    在排查过程中，可能会出现因错误服务自动重启导致内存溢满等连带问题。此时登录云服务商的对实例进行重启，再需通过VNC远程登录修改配置，避免SSH多次触碰重启机制。
