    容器化部署：Docker

    在没有Docker之前，FastAPI服务是直接运行在宿主机的Ubuntu中。虽然我们可以通过python虚拟环境隔离依赖，但服务还是在依赖这服务器本身的python版本与环境配置上的。当项目准备迁移到另一台服务器上的时候，就说不定会遇上“我在我的服务器上能运行，为什么在你的服务器上不行？”这样的问题。

    故此，Docker便是为了解决这样的问题而顺应诞生。它的核心思想是将应用程序以及运行所需的环境一起封装成 Image，再通过 Container 实例运行。这样应用依赖的是 Image，而不是宿主机环境。

    架构变化便类似为

    # before docker               # after docker
Python                        Docker
 └── .venv                     └── FastAPI Container
      ├── FastAPI                       ├── Python
      ├── Uvicorn                       ├── FastAPI
      └── main.py                       ├── Uvicorn
                                        ├── main.py

    1. Docker 的安装与服务管理

    安装指令如下：

    sudo apt install docker.io -y #Docker不是Python项目依赖，不安装在.venv中，而是系统级服务service
sudo systemctl start docker
sudo systemctl status docker
    • 可能会出现docker hub访问失败的问题，即 docker run hello-world time out。ping registry-1.docker.io排查后发现，可能是国内VPS网络没法访问Docker Hub的远古。故nano /etc/docker/daemon.json配置国内的registry mirror。具体有哪些可以用的镜像善用搜索工具。

    2. Image 与 Container

    Image类似模板，是不可修改的运行环境描述。Container是Image启动后的实例。相关指令如下：

    docker images   # 查看手头上的模板
docker ps       # 查看运行中的实例
docker ps -a    # 查看所有实例，包括已终止的实例
docker run -it --name my-ubuntu ubuntu:22.04 bash #进入名为my-ubntu的Container内部的Ubuntu，不是宿主机的Ubuntu

    3. Dockerfile

    Dockerfile是一份能让Docker明白如何自动构建的说明书。然而，如果不立刻 docker build，很难理解每一行到底在干什么。在写Dockerfile之前，需要确然想要打包的service的相关文件是否有疏漏的地方，如果文件遗漏，在生成 image 后无法直接修改镜像内容，通常需要修改 Dockerfile 后重新 build。

    FROM python:3.12
# 在pyhton:3.12版本搭建
WORKDIR /app
# 如果你是一名工程师，拿到一台全新的 Linux 服务器，你会先决定"工作地点"，还是先把文件搬进去？
# 那肯定是先决定工作地点。等效于mkdir /app + cd /app 两个命令
COPY requirements.txt .
# Docker 有一个非常重要的机制叫layer cache，即每执行一层就会形成一层layer。这里先执行requirements.txt是因为依赖并不会天天变，但主体项目会天天变。
# 所以在每一次跑docker建立container的时候，requirements提前写的话这里就会使用以前建立container的时候使用的缓存，docker根本不用重新装fastAPI。docker build就会变快
# 为什么不是MOVE？Docker 这里选择 COPY，其实也体现了一个重要原则：构建 Image 时，不会修改宿主机上的源代码，只会复制一份进入镜像。
# 接下来要让docker执行reuqirements.txt的安装依赖（等效于pip install -r requirements.txt）
RUN pip install -r requirements.txt
COPY . .
# 两个点代表两个不同的当前目录。第一个是host当前目录(~/fastapi-demo)，第二个是image的当前目录(因为前面已经执行了 WORKDIR /app，所以第二个等于/app)
# 我们希望别人运行docker run my-fastapi Docker 知道应该执行哪条命令
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
## 但目前的写法会导致会把当前项目目录中除特殊排除项以外的所有内容复制进 Image，包括我们不太希望打包进去的.venv。解决办法就是在项目目录新建一个叫.dockerignore的文件，功能和.gitignore一样。
    • 确认有没有写requirements.txt记录python application的环境依赖。
    • .venv 不应该打包进 Docker。因为docker在构建image的时候，会重新创建一套干净的python环境。所以也要写.dockerignore。常见的.dockerignore的内容如下
    .venv
__pycache__
*.pyc
.git
.gitignore
Dockerfile
compose.yaml

    虽然对Dockerfile 和 compose.yaml 是否排除有争议。

    4. Build image/ container/ compose

    确认准备内容都做完后，便可docker build -t fastapi-demo:v1 .指令生成image。-t给image命名，.表示build context。生成完成后，可以运行docker images进行检查。 随即，我们可以通过以下指令运行对应的container：

    docker run -d \ 
  --name fastapi-demo \
  -p 8000:8000 \
   fastapi-demo:v1
# \后直接enter。
## -d（detach）：后台运行，不占用当前终端。
## --name fastapi-demo：给这个容器起个名字，方便以后管理。
## -p 8000:8000：把宿主机 8000 端口映射到容器 8000 端口。
## fastapi-demo:v1：运行我们刚刚 build 出来的镜像。

    紧接着就会有一串数字返回，这便是docker container的ID。我们可以通过docker ps和 docker logs fastapi-demo对container进行检查。

    我们可以发现运行container的指令有些繁杂，而且在将来，我们同时使用多种container。故我们会选择把这些指令改写成 docker compose 文件。docker compose 是描述应用由哪些 service 组成，以及这些 service 如何运行和通信的配置文件。Container 是 service 的具体运行实例。新版官方推荐叫 compose.yaml，但很多老项目仍然用 docker-compose.yml。它的内容主体类似如下：

    services:
  fastapi:
    build: .
    ports:
      - "8000:8000"

    除此之外，我们还有以下指令：

    • 检查compose是否能够正确读取配置 docker compose config
    • 创建并启动compose服务！docker compose up --build。up 表示创建并启动服务，--build 表示启动前根据 Dockerfile 重新构建 Image。第一次我们先不加 -d，让日志直接显示在终端里，方便确认 Uvicorn 是否正常启动。但是，这是前台运行模式，会导致目前使用的终端被compose占用，用来持续显示日志，所以需要新建一个terminal继续输入指令和开发。
    • 可能存在build的速度很慢和失败的问题。原因是，build会重新在网络下载FastAPI/ Uvicorn/ Pydantic等依赖，Compose 自己触发的新构建，而且当前构建器、缓存状态或镜像标签与上次不完全一致，所以 RUN pip install 这一层没有复用缓存。国内的VPS会无法通过官方渠道下载以来。
    • 故此，可以考虑把docker file中的 RUN pip install -r requirements.txt 改为RUN pip install -i https://pypi.tuna.tsinghua.edu.cn/simple -r requirements.txt 使用清华的镜像站。

    5. 修改代码并重新部署

    • docker logs <container name> ，就能找到error的情况。虽然docker compose logs也能直接看到。
    • docker compose exec fastapi bash进入容器。
    • 更新.dockerignore文件后，需重新再build一次（这次在后台运行 docker compose up --build -d ）因为 .dockerignore 只在 build 的时候生效。
